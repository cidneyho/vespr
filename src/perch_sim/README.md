# perch_sim

Gazebo simulation of the X500.

## Quick start

1. Open this repo in VS Code and run **Dev Containers: Reopen in Container**.
2. In a VS Code terminal (it is already inside the container), start the sim:
   ```bash
   cd ~/PX4-Autopilot && make px4_sitl gz_x500
   ```
   A Gazebo window opens with the drone, and the terminal shows a `pxh>` prompt.
3. First time only, at the `pxh>` prompt, let PX4 fly without a ground station app:
   ```
   param set NAV_DLL_ACT 0
   ```
4. Wait for `Ready for takeoff!`, then type `commander takeoff`. The drone climbs and hovers. Type `commander land` to bring it down.

To stop the sim, press Ctrl+C in the first terminal.

## Fly it from ROS 2

To fly the sim drone from code, see the test flight in [perch_flight](../perch_flight/README.md).

## Terms

| Term | Meaning |
|---|---|
| PX4 | The autopilot firmware. Same one that runs on our Pixhawk 6C |
| SITL | Software in the loop: PX4 runs as a normal program on your machine, and Gazebo stands in for the real sensors and motors |
| Gazebo | The physics simulator (Gazebo Harmonic, the newer `gz sim`, not Gazebo Classic) |
| `gz_x500` | The simulated Holybro X500, matching our airframe |
| `pxh>` | The PX4 shell that appears in the terminal running SITL |
| QGroundControl (QGC) | Ground station app: map, telemetry, parameters |
| ROS 2 | Toolkit our robot code is built on. Programs talk by publishing messages to named channels |
| Node | One ROS 2 program, such as `perch_flight`'s `fly_square` |
| Topic | A named channel nodes publish to and listen on, such as `/fmu/out/vehicle_local_position` |
| Micro XRCE-DDS Agent | Bridge that turns PX4's internal data into ROS 2 topics (`/fmu/out/*`) and ROS 2 topics into PX4 commands (`/fmu/in/*`) |
| Offboard mode | PX4 mode where an external program sends position or velocity setpoints |
| NED | North-East-Down, PX4's local frame. Up is negative `down`, so 5 m altitude is `z = -5` |


## Perch worlds

Our worlds live in [worlds/](worlds/) and our props in [models/](models/). Start the sim with the script instead of `make`:

```bash
~/vespr/src/perch_sim/scripts/run_sim.sh                    # perch_rod world, gz_x500
~/vespr/src/perch_sim/scripts/run_sim.sh perch_rod gz_x500_depth
```

PX4 only loads worlds from `~/PX4-Autopilot/Tools/simulation/gz/worlds`, so the script symlinks ours there, adds `models/` to `GZ_SIM_RESOURCE_PATH`, then runs `make px4_sitl`.

`perch_rod` is the default world plus one prop: a 4 cm rod, 1.5 m long, top at 1.52 m, held on two posts. It sits 3 m east of the drone's spawn point and runs north-south. In PX4's NED frame that is `y = 3`, `x` from -0.75 to 0.75, top at `z = -1.52`. The rod is static, so it doesn't move when the drone hits it.

`perch_branch` (`run_sim.sh perch_branch`) is a bark-textured tree: a 26 cm trunk 5 m east of spawn, and one limb curving back west toward the drone. The limb leaves the trunk at 1.6 m, rises gently, and tapers from 6.4 cm to 3.6 cm thick. Its clear perch zone is 3.3 to 4.0 m east, 4.9 to 3.9 cm thick, top at about 1.8 m. In NED that is `y` from 3.3 to 4.0, `x = 0`, `z` about -1.8. Two thin twigs stick out of the limb as obstacles. Exact dimensions are in the comment at the top of [models/perch_branch/model.sdf](models/perch_branch/model.sdf).

The branch is generated by [scripts/make_branch_mesh.py](scripts/make_branch_mesh.py). It writes both the visual mesh (`meshes/branch.obj`) and the collision cylinders in `model.sdf` from one layout, so what the camera sees matches what the drone can touch. To change the branch, edit `BRANCHES` in the script, run `python3 scripts/make_branch_mesh.py`, and restart the sim. Don't edit `model.sdf` or `branch.obj` by hand. The bark is [bark_brown_02](https://polyhaven.com/a/bark_brown_02) from Poly Haven (CC0).

Both worlds have a speckled floor, `perch_floor`, because optical flow can't track a plain one. It is generated by [scripts/make_floor.py](scripts/make_floor.py).

### Hook drone

`gz_x500_hook` is the X500 with our perching hook, a forward RealSense-like camera, and a downward optical flow sensor and rangefinder. It flies like the real drone indoors: GPS off, positioned by flow and rangefinder. Its PX4 airframe is [airframes/4920_gz_x500_hook](airframes/4920_gz_x500_hook), which also turns off the ground-station check, so step 3 of the quick start isn't needed.

```bash
~/vespr/src/perch_sim/scripts/run_sim.sh perch_rod gz_x500_hook        # GPS off
GPS=1 ~/vespr/src/perch_sim/scripts/run_sim.sh perch_rod gz_x500_hook  # GPS on, as outdoors
```

The model is generated from `hook.yaml` by [scripts/make_hook_model.py](scripts/make_hook_model.py). Design: [docs/design/flow_rangefinder.md](../../docs/design/flow_rangefinder.md).

### Camera for vision tests

`gz_x500_depth` has a forward RGB camera (IMX214) and a depth camera. To get its images into ROS 2:

```bash
~/vespr/src/perch_sim/scripts/run_sim.sh perch_branch gz_x500_depth
gz topic -l | grep image                  # find the camera topics
ros2 run ros_gz_bridge parameter_bridge <topic>@sensor_msgs/msg/Image[gz.msgs.Image
ros2 run rqt_image_view rqt_image_view    # view it
```

### Adding a prop

1. Make `models/<name>/` with a `model.config` and a `model.sdf`, using `perch_rod` as the template.
2. Include it in a world. Gazebo is ENU (x east, y north, z up), and the drone spawns at the origin:
   ```xml
   <include>
     <uri>model://<name></uri>
     <pose>x y z roll pitch yaw</pose>
   </include>
   ```
   A new world must use the same `<world name="...">` as its filename, or PX4 can't attach to it.
3. Check it before launching: `SDF_PATH=models gz sdf -k worlds/<world>.sdf`. Run it from `src/perch_sim`.

To try a prop without restarting, spawn it into the running sim:

```bash
gz service -s /world/perch_rod/create --reqtype gz.msgs.EntityFactory --reptype gz.msgs.Boolean \
  --timeout 5000 --req 'sdf_filename: "model://perch_rod", name: "rod2", pose: {position: {x: 5, y: 2, z: 0}}'
```

For branch and tree meshes, put the `.dae`, `.obj`, or `.stl` file in `models/<name>/meshes/` and use it as `<mesh><uri>model://<name>/meshes/branch.dae</uri></mesh>` in the visual. Keep the collision as simple shapes, such as cylinders along the limbs. Mesh collisions are slow and contact on them is unreliable.

## QGroundControl (host)

QGC runs on the host, not in the container. The container uses host networking, so QGC finds the simulated drone automatically. Download the x86_64 AppImage from the [QGC install page](https://docs.qgroundcontrol.com/Stable_V5.1/en/qgc-user-guide/getting_started/download_and_install.html). The current AppImage targets Ubuntu 24.04 and later. On 22.04 you need an older release. Prerequisites:

```bash
sudo usermod -aG dialout "$(id -un)"
sudo systemctl mask --now ModemManager.service
sudo apt install -y libfuse2 libxcb-xinerama0 libxkbcommon-x11-0 libxcb-cursor0
```

Run it on the host (the path depends on where you saved the AppImage):

```bash
chmod +x ~/Downloads/QGroundControl-x86_64.AppImage   # first time only
~/Downloads/QGroundControl-x86_64.AppImage
```

If you can't remember where you saved it, run `find ~ -iname "QGroundControl*.AppImage" 2>/dev/null`. Start PX4 SITL first. QGC then connects on UDP 14550 without any setup.

## Next steps

1. **Harder scenes for vision:** a textured ground, more trees, and distractor branches around `perch_branch`.
2. **Perch-approach node:** fly beside the bar, then descend slowly. Same setpoint pattern as `perch_flight`'s `fly_square`, later velocity setpoints.
3. **Model the perching mechanism** once the design exists: copy the X500 model, add links and joints.

Known limit: Gazebo is good for flight dynamics, control logic, and sensor data, and weak at contact detail such as a claw gripping bark. Validate the grip on hardware.
